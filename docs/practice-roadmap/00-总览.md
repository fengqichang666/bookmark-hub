# bookmark-hub 后端练手改造总览

> 目标：把当前的书签管理项目，改造成一个覆盖**后端日常开发核心技术栈**的练手项目。
> 分支：`feature/practice-roadmap`
> 起始日期：2026-07-05

---

## 一、改造理念

- **每个技术点必须落到一个合理的业务场景**，杜绝"为了用而用"。
- **分阶段推进**，每个阶段独立可跑通、可演示、可写进简历。
- **对齐真实生产实践**：分层清晰、有日志、有事务、有异常处理、有文档。

---

## 二、当前项目盘点

### 已有模块

| 模块 | 功能 | 已用技术 |
|---|---|---|
| `auth` | 用户、团队、成员、JWT 登录 | Spring Security、JWT |
| `bookmark` | 书签 CRUD | MyBatis-Plus |

Spring Boot 2.7、MyBatis-Plus、Spring Security、JWT、Flyway、Knife4j (OpenAPI)、基础事务、多表关联。

### 待补齐技术

MQ、Redis、定时任务、调度平台、Excel 导入导出、Elasticsearch、文件存储、限流、分布式锁、WebSocket、AOP 日志、RBAC、回刷脚本、离线跑批、告警通知。

## 三、技术点到业务场景的映射

| 技术点 | 业务场景 | 为什么需要 |
|---|---|---|
| **Redis 缓存** | 首页热门书签、用户 profile | 高频读，缓存扛压 |
| **Redis ZSet** | 书签点击排行榜 | ZSet 天然支持排行 |
| **RabbitMQ** | 加书签后异步抓取网页 title/favicon/desc | 耗时 IO，不能阻塞接口 |
| **MQ 削峰** | 批量导入 1 万条书签，拆消息慢消费 | 防止一把梭打崩数据库 |
| **@Scheduled** | 每小时把 Redis 点击数落库 | 简单单机定时够用 |
| **XXL-JOB** | 每天扫全表检查死链，分片执行 | 集群、失败重试、手动触发、分片 |
| **Redisson 分布式锁** | 同 URL 多人同时抓取时去重 | 防重复消费 |
| **EasyExcel** | 书签 Excel 批量导入导出 | 最常见的业务需求 |
| **Elasticsearch** | 书签全文搜索（标题/描述/URL/标签） | MySQL LIKE 慢且不分词 |
| **MinIO** | 头像、书签封面图上传 | 文件不放数据库 |
| **AOP 操作日志** | 记录谁在什么时间改了什么 | 通用切面，可复用 |
| **RBAC 权限** | 团队 owner / admin / member 角色 + 菜单/按钮权限 | 真实业务标配 |
| **接口限流** | 抓取接口 QPS 限制 | 防爬虫 / 防刷 |
| **WebSocket / SSE** | 团队协作，成员加书签时实时推送 | HTTP 做不到推送 |
| **回刷脚本** | 历史书签补 favicon、补冗余字段 | XXL-JOB 挂一个手动触发 Handler |
| **报表跑批** | 每天凌晨算团队昨日新增数据 → stats 表 | 离线跑批经典场景 |
| **邮件通知** | 团队邀请、死链告警 | 邮件走异步 MQ |
| **软删除 + 归档** | MyBatis-Plus 逻辑删除 + 每月归档 history 表 | 数据治理 |
| **配置中心（简版）** | 系统参数表 + Redis 缓存 + 动态刷新 | Nacos 之前的基础 |

## 四、阶段规划

按依赖关系分五个阶段，每阶段 1-2 周，独立可交付。

### [阶段一：基础增强](./01-阶段一-基础增强.md)（1-2 周）
补齐规范：分层、异常、AOP 日志、Excel 导入导出、软删除、标签模块。

### [阶段二：异步与定时](./02-阶段二-异步与定时.md)（1-2 周）
引入 Redis、RabbitMQ、XXL-JOB，把耗时逻辑异步化，写第一个回刷脚本。

### [阶段三：搜索与文件](./03-阶段三-搜索与文件.md)（1-2 周）
引入 Elasticsearch 做全文搜索，引入 MinIO 做文件存储。

### [阶段四：权限与协作](./04-阶段四-权限与协作.md)（1-2 周）
RBAC 细化、接口限流、WebSocket 实时推送、邮件通知。

### [阶段五：可观测与治理（可选进阶）](./05-阶段五-可观测性.md)
Prometheus + Grafana、SkyWalking、ELK；再往后是拆微服务。

## 五、目录结构调整建议

现在按业务模块分包挺好，继续保持。每个新模块的推荐结构：

```
bookmarkhub/
├── bookmark/
│   ├── controller/     Controller 层
│   ├── service/        Service 层
│   ├── mapper/         Mapper 层
│   ├── entity/         数据库实体
│   ├── dto/            请求/响应 DTO（现在缺）
│   ├── vo/             对外展示对象
│   ├── mq/             消息生产/消费
│   └── job/            定时任务 Handler
├── common/
│   ├── aop/            通用切面（操作日志、限流）
│   ├── config/         配置类
│   ├── exception/      全局异常
│   ├── response/       统一响应体
│   └── util/           工具类
└── infra/
    ├── redis/          Redis 封装
    ├── mq/             MQ 封装
    ├── es/             Elasticsearch 封装
    └── storage/        MinIO 封装
```

## 六、如何使用这份文档

1. 每个阶段是一个独立文档，包含**目标、任务清单、验收标准、参考代码位置**。
2. 每完成一个任务，在阶段文档里把 `[ ]` 改成 `[x]`。
3. 每完成一个阶段，开一个新分支 `feature/phase-N-xxx`，做完合并回 `feature/practice-roadmap`。
4. 遇到不懂的技术点，先看 [`docs/learning-phase1/`](../learning-phase1/) 和 [`docs/learning-phase2/`](../learning-phase2/) 的基础文档。
